All backend features extracted — Flutter is now frontend-only. Build the external backend against this contract.

Previously: Firebase (Auth, Firestore, FCM, Analytics, Crashlytics) + Supabase (Postgres, Storage, Edge Functions). Now: zero Firebase/Supabase in the app. Every table, bucket, edge function, RLS policy, Firestore rule, and realtime subscription below must be re-implemented as REST + storage + push behind ApiConfig.baseUrl. Overview & Goals

Why extraction, what success looks like, what is out of scope.

Goals
  • Remove all Firebase & Supabase SDKs from Flutter (done: pubspec.yaml now has only http + UI deps).
  • Provide a single, versioned REST API that covers every feature listed in BACKEND_PLAN.md + BACKEND_SERVICES.md.
  • Keep UI 100% intact — screens in lib/features/** keep their widgets, now call ApiClient (currently mocked).
  • Preserve security semantics: ownership checks, RLS-like row ownership, and no plaintext card storage.
  • Make rollout incremental: mock → real backend by swapping API_BASE_URL without app code changes.
Non-goals
  • Re-designing UI or navigation.
  • Changing the Arabic UX or business rules (pricing in EGP, governorate filtering, etc.).
  • Building admin dashboard (but API must support it).
Frontend wiring: lib/main.dart no longer calls Firebase.initializeApp or Supabase.initialize. It only calls ApiConfig.init(). Every repository in lib/core/repositories/* now hits ApiClient (currently stubbed with Future.delayed + mock objects).

Why REST? Flutter previously used Firestore snapshots() + Supabase Realtime. External backend can keep realtime via WebSocket or SSE for chat/offers/notifications (§15), but MVP may use polling + pull-to-refresh. The ApiClient is transport-agnostic — add a WebSocket client later if needed.
Source of truth: One DB for the external backend (Postgres recommended). Replicate the 9+ tables (§16) there. Do NOT keep Firestore + Supabase side-by-side — migrate completely.

Security, RLS & Rules

Translate Firestore rules + Supabase RLS to backend authz.

Firestore rules → backend checks
// users/{uid}: read any auth, create if uid==docId, update if uid==owner
// technicians/{phone}: read any auth, create any auth, update if phoneNumber==phone
// requests/{id}: read if userId==uid OR technicianId==phone, create if auth, update if owner or tech
// offers/{id}: read any auth, create if technicianId==phone, update if tech owner
// conversations: read if customerId==uid OR technicianId==phone
// PaymentCards: owner only (userId==uid)
// transactions: technician only (technicianId==phone)
// posts: read any auth, create/update/delete if authorId==uid
// verified: owner only
Supabase RLS → Postgres policies (or app-level)
-- Example (translate to app checks or PG RLS with JWT sub)
-- notifications: owner read, system insert
-- reviews: public read, auth insert/update own
-- promo_codes: public read active, service_role manage
-- support_tickets: owner scoped
-- search_index: public read
-- payment_logs: owner read, system insert
-- appointments: owner scoped
-- After JWT: using (auth.uid()::text = user_id)

Keep is_active AND valid_until > now() for promo visibility, and using (true) → tighten to auth.uid() after JWT.

Must preserve: No plaintext cards, rate-limit OTP, enforce phone ownership on technician writes, sign private bucket URLs (account_verification, request, task_images), validate max_uses/used_count atomically via increment_used_count RPC.
